# U06 Package 3 — explicit historical mapping

Tracking issue #38. Paired Android PR jeresaf/collect#103. Starts at exact promoted U08 development baseline.

The V1 explicit mapping manifest defines an answer-free, bounded, one-to-one mapping from source field path to target field path, with TEXT/INTEGER/DECIMAL/DATE type and exact work, source submission, target version and both XForm hashes. Canonical ASCII representation is domain-separated and ordered by target path, with newline-separated identities and tab-separated rule tuples; reserved metadata, ambiguous rules, unsupported paths and invalid digests are rejected. The Android and backend tests use the same literal canonical vector. This is NOT the existing SignedMappingGrantVerifier V1 format and cannot be used as an operational grant; no signature or authority is implied. Future server-owned recommendation/approval must independently check current project, source XML identity, actor, consent, form hashes, native field inventories, semantics and revocation, and bind the manifest digest to signed authorization. No HTTP endpoint, database migration, grant issuance, answer read or transfer is introduced. Repeat/media/select migration remains a separate qualification boundary within this package.

Explicit inspection extends the existing independent web Project Admin policy and native JavaRosa evidence route with a read-only POST at `/typed-native-candidates/{recommendationId}/explicit-inspection`. Fresh reviewer separation, exact recommendation rehash and denial veto precede trusted form lookup. Exact work/source/target/schema scope and equality with the escalated target set are required. Static policy rejects ambiguous primary instances/refs, rename collisions, dynamic forms and mismatched types; fresh JavaRosa parses both schemas and independently checks source/target leaf types. The conservative server subset blocks globally complex forms even if Android can classify individual paths. Evidence is non-authorizing and no source submission XML is returned. Added synthetic native rename tests and real authenticated HTTP scope tests; no new persistence or positive approval, consent or issuer. Reviewer recommendation currently binds destinations, not explicit source choices; therefore this endpoint is inspection only, not an approval or signed manifest.

V10 provenance: original reviewer binds a canonical explicit proposal to a current immutable recommendation via `/typed-review-recommendations/{recommendationId}/explicit-proposal`. Independent signer inspection refuses substituted rules after binding. `/typed-native-candidates/{recommendationId}/explicit-endorsement` records only exact native compatibility, with reviewer/signer separation, current digests, READY lock, existing denial veto, one immutable row per recommendation and exact retry. Both ledgers are non-authorizing; no operational approval, consent verification, trust enrollment, signing or source answer import. Legacy unbound inspection is advisory only. Work locking serializes these operations against existing denials/completion; source/schema mutation and role-revocation races must be rechecked at any future operational use stage. DB administrator tampering remains outside application-level append-only guarantees.
